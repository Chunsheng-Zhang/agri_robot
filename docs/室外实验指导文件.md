# 农业机器人室外实验指导文件

适用当前仓库的 MGX23 TCP、Yahboom X3、Jetson 手柄映射、4ROS 雷达和 Astra Pro Plus。按当前代码编写，指令基于本机已安装的 ROS 2 Humble CLI 帮助核对。本文件是待执行的实验方案，不是实车验收报告。

## 1. 前端、后端到底在哪里，是否还需要修改

**前后端已完成总览实时数据对接，实车效果仍须按本文件验证。** 首轮室外实验先通过 ROS 2 命令验证核心，Web 在 S09 进行对照。最新三终端启动步骤见 [Web 实时数据显示与启动](Web实时数据显示与启动.md)。

| 位置 | 作用 | 当前实际情况 |
| --- | --- | --- |
| `agri_web/src/main.ts`、`App.vue` | Vue 入口 | 已有前端，不在新 ROS 工作区内 |
| `agri_web/src/router/index.ts` | 路由 | 总览、监控、任务、规划、设备、记录页面已实现；协同作业仍预留 |
| `agri_web/src/views/DashboardView.vue` | 当前系统总览 | 组合路径、机器人、安全状态和任务控制，链接到任务编辑页 |
| `agri_web/src/components/AppHeader.vue` | 页面顶部急停 | 共用 EmergencyControls；未知状态禁用解除、请求以安全服务确认为准 |
| `agri_web/src/components/dashboard/RobotStatus.vue` | 状态卡 | 显示真实经纬度、平面位置、速度和 ROS 航向；过期显示未知 |
| `StatisticsCards.vue`、`TaskList.vue` | 实时统计/任务列表 | 显示观测速度、路径点数、真实任务状态及进度，已移除示例面积和覆盖率 |

状态每秒查询，路径每 2 秒查询；视频使用独立连续流。设备未启动时显示未知或未连接。前端在 Jetson 上运行时，通过其同源代理可供局域网浏览器访问；若前端在笔记本运行，需在 `.env.local` 将代理目标改为 Jetson 实际地址并重启 Vite。

完整操作见 [Web 任务操作与旧 GUI 功能迁移](Web任务操作与旧GUI功能迁移.md)。Web 已提供任务编辑、模式切换、开始/暂停/继续/取消、遥控、运行记录下载和真实电压；不把电压推算为未知电池百分比。页面不替代 ROS 日志、Bag、独立测量或现场停止措施。

## 2. 实验顺序与每阶段启用哪些代码

原则：同一时间只运行一套核心启动。每轮使用独立目录；上一轮先停车、正常结束并保存，再启动下一轮。一次只改一个主要控制参数，每种运动实验至少重复 3 次以便比较。

| 编号 | 验证内容 | 启用代码/模式 | 底盘 | 主要记录与通过依据 |
| --- | --- | --- | --- | --- |
| S00 | 环境、版本、记录链路 | 环境脚本、构建和本文件记录步骤 | 不启动 | 架构、依赖、原点、配置、Bag 能写入 |
| S01 | MGX23 静态稳定性与连续性 | `mode:=base`，MGX23+localization+safety | none | 经纬度/平面位置/航向/时间间隔，静止漂移与跳点 |
| S02 | 航向、坐标方向、安装杆臂 | 同 S01，人工转动/推动车辆 | none | 原始航向与 ROS yaw 对照，东/北位移符号与距离 |
| S03 | 手柄/雷达/相机接入和无动力控制链 | base+三个设备 | none | 按键、距离方向、锁定、图像状态；没有驱动订阅端 |
| S04 | 低速手动与急停 | base+手柄+雷达+原始底盘 | yahboom_x3 | 指令与实车方向、松手停车、急停/复位/断联 |
| S05 | 障碍物、超时、恢复 | S04；随后自主模式补验证 | yahboom_x3 | 四方向停车、扫描无效/超时、锁定与人工恢复 |
| S06 | 独立 RTK 多点导航 | `mode:=waypoint`+基础设备 | yahboom_x3 | 到点、减速、停留、顺序、暂停/取消、终点误差 |
| S07 | 独立 Pure Pursuit 基线 | base+新 path_tracker+原 CSV 发布脚本 | 先 none，再 yahboom_x3 | 直线跟踪误差、轨迹、完成判断；不启动覆盖规划 |
| S08 | 覆盖规划与完整跟踪 | `mode:=coverage`+基础设备 | 先 none，再 yahboom_x3 | 边界与地头净空、参考路径、跟踪误差、任务结束 |
| S09 | Web 对照验证 | 上述 ROS+FastAPI；Vue 只观察已接入部分 | 先静止 | API 与 ROS 状态一致，未知不误显示；视频单独验证 |

第一次外场至少做完 S00–S05。S06 必须建立在定位、航向、运动符号和停车验证通过之后。S08 不应是第一次带动力的实验。

原 `test.md`、`test_out.md` 中有早期混合工作区和直接发 `/cmd_vel` 的命令；本轮不要与它们混用。现在只 source `scripts/setup_environment.bash`，不再额外 source `robot_sim/install`，也不要启动旧 Pure Pursuit、原手柄可执行文件、整车 laser_bringup 或额外里程计 TF。不要向最终 `/cmd_vel` 或 `/base/driver_cmd_vel` 手工发布运动命令。

## 3. S00：场地、平台和准备工作

在开阔、与无关人员隔离的区域，低速验证；由一人操作、一人观察并负责实车急停/断动力。先在底盘无动力或车轮离地条件验证停止逻辑，再落地。软件急停不能替代硬件急停；原底盘固件接收超时是否可靠，需要单独验收。

### 3.1 平台与驱动

```bash
cd /home/zhang/agri_robot
source scripts/setup_environment.bash
uname -m
file yahboomcar_ros2_ws/software/library_ws/install/ydlidar_ros2_driver/lib/ydlidar_ros2_driver/ydlidar_ros2_driver_node
file yahboomcar_ros2_ws/software/library_ws/install/astra_camera/lib/astra_camera/astra_camera_node
file yahboomcar_ros2_ws/software/library_ws/install/web_video_server/lib/web_video_server/web_video_server
bash scripts/build_core.bash
```

现仓库三个原厂设备程序为 aarch64。应在对应 Jetson 上运行；x86_64 主机不能直接执行这些 ARM 程序。若在 x86 上实验，须先按本机架构构建原驱动及依赖，不能用“新 Python 核心构建成功”代替硬件驱动可运行。

核对 `/dev/myserial`（原 Rosmaster 库默认串口）、`/dev/ydlidar`、USB 相机和手柄接收器、网络 `172.16.1.250:9000`。设备名与权限以现场为准。不要为满足启动而盲目改设备映射。若原底盘报 `Rosmaster_Lib` 导入失败，使用启动参数 `rosmaster_pythonpath:=/home/zhang/agri_robot/robot_sim/src`；已能运行原命令则无需该参数。

### 3.2 每轮建立独立目录

下面在实验主机执行。S00 可替换为 S01、S04 等；每轮重新执行，mktemp 后缀保证不覆盖旧数据。

```bash
cd /home/zhang/agri_robot
source scripts/setup_environment.bash
export ROS_DOMAIN_ID=0
export ROS_LOCALHOST_ONLY=1
mkdir -p /home/zhang/agri_robot/data/experiments
export RUN="$(mktemp -d "/home/zhang/agri_robot/data/experiments/$(TZ=Asia/Shanghai date +%Y%m%d_%H%M%S)_S00_XXXXXX")"
mkdir -p "$RUN"/{config,raw,paths,tracks,safety,ros_logs,bag,notes,media,checks}
export ROS_LOG_DIR="$RUN/ros_logs"
cp agri_robot_ws/src/agri_bringup/config/system.yaml "$RUN/config/system.yaml"
cp docs/templates/室外实验_rosbag_qos.yaml "$RUN/config/rosbag_qos.yaml"
cp docs/templates/室外实验记录表.md "$RUN/notes/record.md"
printf '%s\n' "$RUN"
```

`RUN` 是这次打印出的完整实际路径。**每个新终端都需要 source 环境，并将 RUN、ROS_DOMAIN_ID、ROS_LOCALHOST_ONLY、ROS_LOG_DIR 设置为本轮相同值**；环境变量不会自动传播到独立终端。不要在录制终端重新创建另一轮目录。

这里让核心和记录器都运行在 Jetson 上；电脑浏览器通过 HTTP 访问，不需要跨机 DDS。若确需跨机 ROS，所有相关终端使用相同 domain，并按网络配置更改 ROS_LOCALHOST_ONLY；不要只改一个终端。

保存版本和未提交源码，避免只记 commit 而漏掉当前尚未提交的新包：

```bash
git rev-parse HEAD > "$RUN/config/git_commit.txt"
git status --short > "$RUN/config/git_status.txt"
git diff -- agri_robot_ws mgx23_ws agri_backend agri_web scripts docs > "$RUN/config/tracked_changes.patch"
tar --exclude='__pycache__' --exclude='*.pyc' --exclude='.pytest_cache' \
  -czf "$RUN/config/source_snapshot.tar.gz" \
  agri_robot_ws/src mgx23_ws/src/mgx23_driver agri_backend \
  agri_web/src agri_web/package.json agri_web/vite.config.ts scripts
```

### 3.3 修改本轮配置副本

编辑 `$RUN/config/system.yaml`，不要直接修改实验中的运行参数。固定原点、安装校准和硬件安全参数为只读，修改 YAML 后须正常重启本轮核心。Web 任务参数仅在待命时通过已验证的参数服务应用；不要用任意 `ros2 param set` 推断所有内部对象都会更新。统一启动现在常驻两类控制器，mode 只是初始选择，勿另开重复节点。

| 配置项 | 外场要求 |
| --- | --- |
| `/**.origin_latitude/longitude` | 改为本场地选定的固定原点，记录来源和实际值；整轮保持不变 |
| `localization.heading_offset` | S02 校准 INS 箭头与车体前向偏角；rad |
| `localization.antenna_x/y` | 实测 base_link 到天线的车体坐标杆臂；m |
| `laser_x/y/z/yaw` | 实测雷达安装；默认仅来自原厂模型，不表示已完成实车标定 |
| `safety.body_length/body_width/footprint_margin` | 使用实际车体/附件尺寸 |
| `allow_lateral` | 当前 X3 为 true；双履带迁移时应 false |
| `safety.max_linear_speed/max_lateral_speed` | 首轮可降到 0.10 m/s |
| `safety.max_angular_speed` | 首轮可降到 0.30 rad/s |
| `waypoint.max_linear/min_linear/max_angular` | 首轮 0.10 / 0.02 m/s、0.30 rad/s，且不超过安全层限幅 |
| `path_tracker.speed/max_angular` | 首轮 0.10 m/s、0.30 rad/s |
| `stop_distance/resume_distance` | 初始 0.8/1.2 m；是车体外缘净空，不直接等于雷达量程 |
| `scan_timeout/sensor_timeout/joy_timeout` | 初始 0.5 s；实测软件延迟与物理制动另外记录 |
| `mgx23_node.raw_log_directory` | 在该节点 ros__parameters 下新增，填写**本轮实际路径** `…/raw` |

例如给 mgx23_node 新增 `raw_log_directory: /home/zhang/agri_robot/data/experiments/实际本轮目录/raw`。YAML 不会展开 `$RUN`，不能直接写 `raw_log_directory: "$RUN/raw"`。

若首次到现场尚不知道可用原点，可以在底盘未启动时，先单独运行 MGX23 取得参考：

```bash
ros2 run mgx23_driver mgx23_node --ros-args \
  -p "mgx23_node:raw_log_directory:=$RUN/raw"
```

在另一个相同环境终端查看 `/mgx23/position`，按稳定数据及测量依据选定原点、写入本轮副本。随后 **Ctrl+C 停止这个临时驱动**，再启动完整核心；不要让两份 MGX23 驱动同时发布。参考点采集过程也应录制或在记录表标注，后续导航过程中不再改变原点。

当前 MGX23 原始 status 不作解状态判定，NavSatFix.status 仍为 -1，`require_fix_status` 为 false；`/localization/valid=true` 只证明当前结构、数值和时效检查通过。记录设备实际定位解证据；不能把该 Bool 当作 RTK 固定解证明。accuracy 字段的统计含义/单位仍需确认，阈值 0.5 也不能当作已验收的 0.5 m 精度标准。

## 4. 全阶段共用：如何记录数据

### 4.1 核心 rosbag：每次任务前先启动

新开记录终端，设置为本轮相同环境和 RUN。目录 `bag/core` 交给 rosbag 创建，**不要提前 mkdir 这个最终目录，也不要复用已存在的同名 bag**。

```bash
ros2 bag record -s sqlite3 -o "$RUN/bag/core" \
  --max-bag-duration 300 --max-bag-size 1073741824 \
  --qos-profile-overrides-path "$RUN/config/rosbag_qos.yaml" \
  /mgx23/position /mgx23/attitude /mgx23/velocity \
  /mgx23/attitude_stamped /mgx23/velocity_stamped /mgx23/status /mgx23/accuracy \
  /odom /localization/valid /localization/origin /tf /tf_static \
  /joy /manual/status /control/manual/cmd_vel /control/web/cmd_vel \
  /control/waypoint/cmd_vel /control/tracking/cmd_vel \
  /cmd_vel /base/driver_cmd_vel /vel_raw \
  /emergency_stop /safety/emergency_stop /safety/status \
  /safety/obstacles /safety/nearest_distance /safety/obstacle_stop /safety/events \
  /scan /reference_path /waypoint/targets /tracking/error \
  /waypoint/status /tracking/status /planning/status /camera/status /parameter_events
```

看到 recorder 已订阅本阶段必需话题后，才开始任务或发起规划。未启用模块的话题本轮不存在属于正常现象；但本阶段必需话题计数为 0 不能当作记录成功。不要使用 `--no-discovery`，因为部分任务节点/话题稍后才启动。

默认不录原始图像和反复携带完整历史的 `/tracked_path`、`/waypoint/trajectory`，以免影响控制和迅速填满磁盘。位姿以 `/odom` 逐点记录，两个控制器另外按配置写 CSV，可重建实际轨迹；参考路径和目标点仍必须录制。QoS 模板兼容原 CSV 路径发布器（volatile）与覆盖适配器（transient-local），路径记录必须开始于规划/发布之前。

### 4.2 相机可选记录

只在需要视频证据且存储/负载允许时，第二个记录器另录 30–60 s：

```bash
ros2 bag record -s sqlite3 -o "$RUN/bag/camera" \
  --max-bag-duration 60 --max-bag-size 536870912 \
  --qos-profile-overrides-path "$RUN/config/rosbag_qos.yaml" \
  /camera/color/image_raw /camera/status
```

640×480、bgr8、30 fps 的裸图像载荷约 27.6 MB/s，即约 1.66 GB/min，未计额外开销。浏览器 MJPEG 显示不等于自动保存了视频。外部手机拍摄的实车过程、卷尺/地标和设备指示灯另存 `media/`，并在记录表注明拍摄时间和对应 RUN。

### 4.3 当前代码自动保存与不保存的内容

| 数据 | 当前生成方式 | 本方案保存位置 | 默认不配置时 |
| --- | --- | --- | --- |
| 原始 NAVI 字节流 | MGX23 `raw_log_directory`，唯一命名 `.bin` | `raw/mgx23_时间.bin` | 不保存 |
| ROS 消息、定位、速度、状态、雷达 | 上述手动启动 rosbag | `bag/core/metadata.yaml` 和 `.db3` 分片 | 不保存 |
| 完整覆盖参考路径、原点、方向标记 | 成功规划且设置 `path_directory` | `paths/coverage_时间.json` | 不保存 JSON；仍可发 Path |
| Pure Pursuit 实际轨迹、误差和坐标基准 | 跟踪任务开始且设置 `trajectory_directory` | `tracks/track_时间.csv` 与同名 `.json` | 不保存 CSV/元数据 |
| 安全事件 | `event_directory` 与 ROS 日志 | `safety/safety_时间.jsonl` | 无独立 JSONL，仅 ROS 日志/Topic |
| 节点输出 | `ROS_LOG_DIR`；启动终端 tee | `ros_logs/` | 通常落在 `~/.ros/log` |
| 多点导航实际轨迹/目标索引/误差 | 配置 `trajectory_directory` 后自动记录 | `tracks/waypoint_时间.csv` 与同名 `.json` | 不配置目录时从 `/odom` Bag 提取 |
| 手动实际轨迹 | 未专设手动 CSV | 从 `bag/core` 的 `/odom` 提取 | 不自动生成任务 CSV |
| 相机 Image | 可选相机 rosbag | `bag/camera/` | 相机驱动/视频桥本身不存视频 |
| 人工操作、独立测量、失败原因 | 填写记录表 | `notes/record.md`、`media/` | 不自动生成 |
| Web 提交地块 | 原后端固定写入一个文件 | `data/field_boundary.json`，每次成功提交覆盖旧内容；需另复制到本轮 config | 不会自动归档，也不自动规划 |
| Web 状态 API | 内存缓存 | 需要时手动保存到 `checks/` | 不存为实验数据库或历史文件 |

`track_*.csv` 列为 `stamp,x,y,yaw,cross_track,heading_error,progress`，位置/进度 m、角度 rad。stamp 为 ROS 主机时间秒，设备原始时间为 hhmmss.ss，两者不能直接相减。CSV 每 20 条刷新，任务结束/正常关闭时关闭文件；不要靠强杀保证尾部数据完整。`/tracking/error.vector.x` 是当前路径段距离，CSV 的 cross_track 是有符号横向量，端点附近两者不一定相同。

同名 `track_*.json` 保存 `projection`（原点经纬度和 EPSG）、`frame_id=map`、`position_reference=base_link`、单位与该任务接收的完整参考路径 `reference_path.points`。归档时 CSV 和 JSON 成对保留。分析时先确认规划 JSON 与轨迹元数据的 `projection` 完全一致；也可直接使用轨迹元数据中的参考路径与同名 CSV 叠加，避免选错另一次规划。两者的 x/y 已在同一固定基准下，不得分别按各自起点重新归零。若原点不同，应先按明确的投影和原点转换，不能直接叠加。

全局原点不在 Web 修改。整轮使用 `config/system.yaml` 中相同的固定值；相关节点运行时拒绝修改原点和工作半径。更换原点需停车、取消任务并重启整套核心。定位位置代表经天线杆臂校正后的 `base_link`；直接分析原始天线位置时还需应用同一安装偏移。

本轮目录树应类似：

```text
data/experiments/日期时间_S阶段_唯一后缀/
├── config/      system.yaml、目标点、边界、独立路径、QoS、版本和源码快照
├── raw/         mgx23_*.bin
├── paths/       coverage_*.json
├── tracks/      track_*.csv 与同名坐标基准/参考路径 .json
├── safety/      safety_*.jsonl
├── ros_logs/    节点日志、launch_console.log
├── bag/core/    metadata.yaml、所有 .db3 分片
```

### 启动终端

此时没有底盘驱动，不执行导航；没有雷达时安全层不允许运动是正常结果。MGX23 原始数据目录已按第 3 节写入本轮 YAML 才会产生 `.bin`。

### 检查终端

```bash
ros2 topic echo /mgx23/position --once
ros2 topic echo /mgx23/attitude_stamped --once
ros2 topic echo /localization/valid --once
ros2 topic echo /localization/origin --once --qos-durability transient_local --qos-reliability reliable

```

TF 命令分别运行，Ctrl+C 结束该查看进程再执行下一条。map→odom 应为恒等；odom→base_link 应随 GNSS/INS 改变。只允许 localization 提供这组定位 TF，不启动轮式里程计/EKF。

用 `ros2 topic hz /mgx23/position`、`/mgx23/attitude_stamped`、`/odom` 各测约 30 s，将输出另存 `checks/`。手册给的是最高 50 Hz，不是本次实际频率；驱动 200 Hz 轮询也不代表发布 200 Hz。若原始数值质量过滤导致丢帧，记录 `.bin` 与 ROS 消息的差异，不要只提高阈值让实验“通过”。

S01 静止采集建议 5 min：

1. 固定车体与朝向，记录开机、初始化、状态稳定的人工时间点。
2. 记录 x/y 的均值、标准差、P95 距均值偏差、最大跳变和连续数据间隔；分别分析初始化段和稳定段。
3. 保存实际定位解的外部证据。仅有设备自身输出时，报告“静态离散/重复性”，不能报告独立绝对定位精度。
4. 检查 `.bin` 不为空、Bag 必需话题在增长、`localization/valid` 稳定；存在明显异常则不进入自主阶段。

S02 依次把车头对准已知方向，或在明确测定的场地轴线上推行；每个方向静止记录约 30 s：

| 方向 | 用户提供定义下的 MGX23 航向（约） | ROS yaw（约） |
| --- | --- | --- |
| 北 | 0 | +π/2 |
| 东 | +π/2 | 0 |
| 南 | 接近 ±π | -π/2 |
| 西 | -π/2 | 接近 ±π |

这里是近似对照，实际转换还考虑 UTM 网格收敛角和安装偏角；不能把小的网格角差直接当作 INS 错误。向已知东向推行时 x 应主要增加，向北推行时 y 应主要增加。用卷尺标出 3–5 m 段，比较平面位移、方向和回到起点后的闭合偏差。检查车体旋转时杆臂补偿后的 base_link 是否出现不合理绕圈。

**本阶段放行条件：** 数据连续、坐标方向正确、前向轴与航向一致、固定原点一致，且记录链路已验证。具体精度目标在记录表提前填写；当前代码没有替你设定一个已验收的厘米级合格标准。

## 6. S03：三设备与安全链无动力验证

正常关闭上一轮核心与记录器；新建 S03 目录并配置后，仅运行这一套：

```bash
bash scripts/start_core.bash mode:=base chassis:=none \
  params_file:="$RUN/config/system.yaml" \
  start_joy:=true start_lidar:=true start_camera:=true start_video:=true \
  event_directory:="$RUN/safety" \
  2>&1 | tee "$RUN/ros_logs/launch_console.log"
```

使用本轮核心 Bag；相机短片按需另录。保存以下输出到 `checks/`：

```bash
ros2 node list
ros2 topic info /cmd_vel --verbose
ros2 topic info /base/driver_cmd_vel --verbose
ros2 topic info /scan --verbose
ros2 topic echo /manual/status --once
ros2 topic echo /safety/status --once
ros2 topic echo /safety/obstacles --once
ros2 topic echo /camera/status --once
```

`/cmd_vel` 应只有 safety 一个发布者，`/base/driver_cmd_vel` 只有 chassis_adapter 一个发布者；本阶段应没有底盘驱动订阅端。手柄 `/joy`、雷达 `/scan` 和相机的真实 QoS 以 info 输出为证，若发布/订阅可靠性不兼容，先解决数据接收，不能继续运动。

逐项验证：

- **手柄：** `ros2 topic echo /joy` 核对数组索引。Jetson 映射至少需要 3 个 axes、15 个 buttons；0 为拟定新急停，3 为拟定复位，9 原手动切换，7/11 灯光/蜂鸣器，13/14 档位。先验证按键数组与原功能，再验证安全状态。
- **急停：** 按 0 锁定，松开保持锁定；摇杆偏转时长按 3 不应解除；回中并松开急停后按 3 保持约 1 s 可请求解除。解除后 owner 仍为空、最终速度为零。随后明确按 9 才申请手动权限。
- **雷达：** 在已测量的前/后/侧位置放置可稳定被雷达识别的静态目标。检查 `global_range` 为雷达原点距离，front/rear 为 base_link 扇区径向距离，停车阈值另按车体净空解释。全无效或错误 frame 不应显示 valid=true。
- **相机：** 在 rqt_image_view 选择 `/camera/color/image_raw`，浏览器访问 `http://Jetson地址:8080/stream?topic=/camera/color/image_raw&type=mjpeg`。拍摄带秒表的场景估计显示延迟；浏览器有连接不等于相机帧仍在更新。
- **断流：** 分别测试手柄接收器断开、手柄电源关闭、雷达停扫和相机断流。特别是无线手柄：如果关闭手柄后接收器仍生成新时间戳的旧值，当前“Joy 心跳正常”不能证明实体手柄在线；必须记录该失败并补足断联检测后再依赖该通道。

无动力阶段先观察 `/cmd_vel`、`/base/driver_cmd_vel` 和安全锁定，确认流程无误。相机丢帧只应改变相机状态，不应参与导航控制。此阶段的 `.bin`、Bag 和 JSONL 应能够解释每次人工操作的时间点。

## 7. S04：低速手动运动、急停与实际制动

前置条件为 S01–S03 通过，底盘动力可由观察人切断，控制限速已按本轮配置降低。首轮先车轮离地验证符号和停止，再在开阔地落地。新建 S04 目录，启动：

```bash
bash scripts/start_core.bash mode:=base chassis:=yahboom_x3 \
  params_file:="$RUN/config/system.yaml" \
  start_joy:=true start_lidar:=true \
  event_directory:="$RUN/safety" \
  2>&1 | tee "$RUN/ros_logs/launch_console.log"
```

这会直接复用原 `Mcnamu_driver_X3` 并 remap 输入。不要再开第二个原始底盘进程占用同一串口。

1. 先启动记录；确认 startup 急停锁定、三个速度分量为零。
2. 摇杆回中，按 3 长按请求解除；确认实际安全状态，不以按钮动画代替。
3. 明确按 9 申请手动权限，确认 owner=manual；分别短时前进、后退、左/右旋转、X3 左/右横移，逐次回中。
4. 每种方向记录原手柄输入、输入速度、最终速度和实际动作；/cmd_vel 是指令，/vel_raw 是原底盘反馈，都不是独立真实轨迹。轨迹仍来自 MGX23 的 /odom。
5. 在 0.10 m/s 上限下，按 0 急停，记录事件到最终指令归零的延迟，以及车体实际停止时间、卷尺量得的停车距离。松开按钮不恢复；复位后仍保持停止，重新按 9 才允许运动。
6. 记录连续按住档位键时是否只切换一次；保留原灯光、蜂鸣器和档位功能。
7. 在观察人可立即切动力的条件下，分别验证松手、手柄断联、控制程序异常等停车。先无动力验证异常，再做必要的最低速度实车验证。不要通过杀死整个核心来代替手柄失联试验。

在表格中分别填写“软件命令归零”和“实车停止”，不能把前者当作后者。任何非预期运动、方向错误或停车失败都应结束本轮并保留失败数据。

## 8. S05：方向相关障碍停车、雷达超时和恢复

沿用 S04 的代码组合，但新建 S05 目录、记录本轮参数；相机可选。用稳定静态目标、卷尺标记测试位置，避免人员充当障碍。先把目标摆好，再由低速车接近；不要把手伸入行驶扫掠区域。

| 工况 | 验证操作 | 应有结果 |
| --- | --- | --- |
| 前进 | 只在后方放近目标，再在前方放目标 | 后方最小距离不能单独阻止直线前进；前方净空小于停车阈值则停车 |
| 倒车 | 只在前方放近目标，再在后方放目标 | 根据后方运动区域停车 |
| 横移 | 左/右侧分别放目标 | 根据 vx/vy 对应移动方向检测，保留 X3 横移能力 |
| 原地旋转 | 在车体角部扫掠区域附近放目标 | 检查完整旋转区域，不能只看前方 |
| 障碍移走 | 距离越过恢复阈值并保持 | 仍锁定，不自动恢复；显式清障后手动还须回中重新按 9 |
| 雷达停扫/无效 | 先无动力停扫，再低速受控验证 | 锁定停车，恢复扫描本身不恢复运动 |
| 自主遇障 | 在 S06/S07 运行段追加本项 | 原任务 PAUSED、保留进度；清障复位后仍需 resume |

检查 `ros2 service list -t`，确认原 4ROS 提供下面接口时，可在无动力/受控试验中暂停与恢复采样：

```bash
ros2 service call /stop_scan std_srvs/srv/Empty '{}'
ros2 service call /start_scan std_srvs/srv/Empty '{}'
```

必须实测 `/scan` 是否停止更新，不凭服务返回空响应认定断流已发生。不要关闭 safety 或底盘适配节点制造雷达超时。观察 sensor_timeout 等设计值、ROS 传输/控制周期和实际刹停的区别；0.5 s 配置不是整个物理系统 0.5 s 内停止的保证。

清障命令：

```bash
ros2 service call /safety/obstacle/reset std_srvs/srv/Trigger '{}'
```

默认要求恢复距离大于 1.2 m 且连续有效 1 s，过早复位应被拒绝。自主任务随后执行 `/waypoint/resume` 或 `/tracking/resume`；手动则回中并重新选择手动。急停是另一把锁，若曾急停则需先按急停复位流程处理，任务失去权限后应重新 start，不是自动 resume。

记录每种工况至少 3 次：原始距离、车体净空、检测/停车事件 stamp、最终命令归零 stamp、物理停止时间/距离、锁定和人工恢复过程。数据在 core Bag、安全 JSONL、记录表和外部视频中对应起来。

## 9. S06：独立多目标点导航

### 9.1 目标点准备

先用现场测量或带来源记录的 MGX23 采集，选择空旷区域中的 2–4 个点，首轮相邻点约 3–5 m，有清楚的地面标记。创建 `$RUN/config/waypoints.yaml`：

```yaml
# 模板中的占位符全部替换成现场数值后，才是可使用的 YAML。
waypoints:
  - latitude: <P1实际纬度>
    longitude: <P1实际经度>
    dwell_time: 2.0
  - latitude: <P2实际纬度>
    longitude: <P2实际经度>
    dwell_time: 2.0
```

不要直接使用包内旧地块样例，除非本次现场和数据确实相符。Web 可预览目标点并在任务启动后显示 `/waypoint/targets`，仍需核对转换结果、点序和实地标记。若目标点也用同一 MGX23 采集，报告到点结果时应区分“系统自身定位闭环误差”和“独立测量的实际到点误差”。

### 9.2 启动与操作

```bash
bash scripts/start_core.bash mode:=waypoint chassis:=yahboom_x3 \
  params_file:="$RUN/config/system.yaml" \
  waypoints_file:="$RUN/config/waypoints.yaml" \
  trajectory_directory:="$RUN/tracks" \
  start_joy:=true start_lidar:=true \
  event_directory:="$RUN/safety" \
  2>&1 | tee "$RUN/ros_logs/launch_console.log"
```

先录制 Bag；完成安全检查和急停解除，确保没有手动 owner 后开始：

```bash
ros2 service call /waypoint/start std_srvs/srv/Trigger '{}'
ros2 topic echo /waypoint/status
```

服务返回成功只表示进入申请流程；确认状态 RUNNING、owner=waypoint。任务应按点序运行、接近点减速、到达后停车停留、进入下一点；最后 COMPLETED 且最终指令为零。

按下面次序分轮验证，不在第一次任务中同时制造全部故障：

1. 单段直线/两点顺序到达。
2. 增加一个转向目标，核查原地对准与转弯速度。
3. 暂停、继续，目标序号不应无故跳变。
4. 取消、重新 start；当前 start 会重读文件并从第一个目标重新开始，不是从原索引自动续跑。
5. 自主运行段遇障，验证 PAUSED、清障复位、明确 resume；进度保留。
6. 手动按钮 9 明确抢占；原自主任务应失去控制权，不在退出手动后自动恢复。
7. 先无动力验证定位断流，再按受控条件验证运行中断流停车。恢复定位后需要明确重新 start。

```bash
ros2 service call /waypoint/pause std_srvs/srv/Trigger '{}'
ros2 service call /waypoint/resume std_srvs/srv/Trigger '{}'
ros2 service call /waypoint/cancel std_srvs/srv/Trigger '{}'
```

记录目标索引、距离、航向误差、到达时刻、停留时间、实际终点与标记位置误差、总时长和所有人工干预。该模式现在生成 `waypoint_*.csv` 与同名原点/目标点元数据；列为 `stamp,x,y,yaw,target_index,distance,heading_error`，目标索引从 0 开始。定位与控制全历史仍以 `bag/core` 为主。

创建 `$RUN/config/straight.csv`，表头必须为 `x_m,y_m,yaw_rad`。以下示例只适用于确认车体起点位于 map 的 (0,0)、向网格东向 +X 的 5 m 都在实验安全区域内的情况；否则按实际起点 x0/y0 和方向修改各行：

```csv
3.0,0.0,0.0
```

这里是已经转换后的 map 米制坐标，不是经纬度，也不是 UTM 绝对 Easting/Northing。直线可使用这些稀疏点，跟踪器内部按线段取前视点；后续曲线路径应有足够采样并验证连续性。首次不要用带锐角、反向段或起点不明的长路径。

## 11. S08：覆盖规划与实车完整跟踪

### 11.1 边界与参数

从现场取得按边界顺序排列的经纬度，记录来源。创建 `$RUN/config/field.yaml`，格式为 `points:` 下的 latitude/longitude 点列；至少三个不同点，通常先用简单凸四边形，逐步增加复杂度。所有占位值必须替换成实际测值。

```yaml
points:
  - {latitude: <角点1纬度>, longitude: <角点1经度>}
  - {latitude: <角点2纬度>, longitude: <角点2经度>}
  - {latitude: <角点3纬度>, longitude: <角点3经度>}
  - {latitude: <角点4纬度>, longitude: <角点4经度>}
```

前端坐标初始为空，应填写本次场地的实际边界。边界、固定原点、机器人和目标点必须来自同一处场地；当前超过 5 km 工作半径会被拒绝。若通过 Web 输入，立即将 `data/field_boundary.json` 归档到本轮 config，并在 `boundary_file` 指向该归档副本；提交本身不会触发规划。

初始覆盖参数在本轮副本中核对：operation_width、min_turning_radius、headland_width、swath_angle、sampling_distance、default_turn_point_distance。地头 3 m 是现有样例通过的参数，不是任意地块通用保证；很小的地块可能被地头内缩耗尽。先选足以保留地头和作业条带的现场区域。

Yahboom 验证时未带真实农机具，operation_width 代表实验条带间距；不能把规划区域自动等同于实际完成农艺作业面积。当前有限半径 Dubins 路径是平滑转弯策略，不代表履带必须服从阿克曼机械约束；原地调头属于另一个明确动作策略，不通过把半径简单设零实现。

### 11.2 无底盘只规划

```bash
bash scripts/start_core.bash mode:=coverage chassis:=none \
  params_file:="$RUN/config/system.yaml" \
  boundary_file:="$RUN/config/field.yaml" \
  path_directory:="$RUN/paths" trajectory_directory:="$RUN/tracks" \
  start_joy:=true start_lidar:=true \
  event_directory:="$RUN/safety" \
  2>&1 | tee "$RUN/ros_logs/launch_console.log"
```

录制先开始，再请求：

```bash
ros2 service call /planning/plan std_srvs/srv/Trigger '{}'
ros2 topic echo /planning/status
```

确认状态 SUCCEEDED、路径非空、`paths/coverage_*.json` 真实生成。在 RViz 中以 map 为 Fixed Frame，查看 `/reference_path`、机器人 TF、LaserScan；路径文件同时保存原点/EPSG，可据此离线叠加边界检查。

验证作业条带间距与方向、地头曲线、路径点顺序、孔洞/边界净空和起点位置。规划失败应保留 FAILED 原因；不能为了得到路径而去掉净空检查。规划成功也不代表整条路径已实车验证。特别是机具扫掠、长车体形状和雷达测量平面之外的障碍仍需另行考虑。

### 11.3 有底盘低速跟踪

规划检查通过后，正常停止无底盘轮次并新建实车轮次，使用相同经过核验的边界、原点和参数，再以 `chassis:=yahboom_x3` 启动同一 coverage 命令。路径会重新规划，必须检查本次输出，不能假设与上一轮完全相同。

1. 先录制、再规划。
2. 用手柄低速接近本次路径起点，确认姿态与路径方向；当前没有自动生成到起点的安全通行路径。
3. 退出手动，确认无 owner、急停已解除、障碍未锁定、定位/雷达/手柄安全通道有效。
4. 明确开始跟踪：

```bash
ros2 service call /tracking/start std_srvs/srv/Trigger '{}'
```

观察误差、进度、速度限幅和完成判断。先完成几条条带的短任务，再逐步扩展，保留失败轮次。跟踪器仅支持前进路径，反向段会被拒绝。

分别验证暂停/继续、遇障后保留进度、清障人工复位和继续、取消、终点停车。只要异常偏离、定位跳变或恢复后自行动作，就结束本轮。默认 max_path_error=2 m 不一定适合小试验区，需结合 S01 的定位噪声、路径走廊宽度和研究要求设定，记录实际值。

最终数据：本次边界和参数在 config，规划结果在 paths，实际跟踪与误差在 tracks，完整控制和测量在 core Bag，安全事件在 safety。地头预留区的“通行”不能当作已作业覆盖，报告中分别统计。

## 12. S09：后端、前端和视频的静止对照验证

首轮 Web 验证保持实车停止，ROS 核心先启动。后端会按参考路径发布者的 QoS 切换订阅，以接收仍在线发布者保留的最后一次规划；原 CSV 发布器的 volatile 周期发布也保持兼容。发布者退出后无法补收已消失的历史，必要时重新发布路径。

### 12.1 后端代码与启动

在 Jetson 另开终端，设置与核心相同的 domain/环境；使用你部署时的 Python 环境。之前临时 `/tmp` 下的测试虚拟环境不是持久部署环境。

```bash
cd /home/zhang/agri_robot
source scripts/setup_environment.bash
# 如需激活自己的 agri_backend/.venv，在这里激活；先检查 ROS 与 Web 依赖均可导入。
python3 -c 'import rclpy, fastapi, uvicorn; print("ROS/Web imports OK")'
cd agri_backend
python3 -m uvicorn main:app --host 0.0.0.0 --port 8000 \
  2>&1 | tee "$RUN/ros_logs/backend_console.log"
```

如依赖检查失败，先解决持久环境的 FastAPI/Uvicorn 和 ROS Python 兼容性；不要运行一个 ROS 未连接的后端并把页面在线误认为机器人在线。浏览器可先查看 `http://Jetson地址:8000/docs`，这是 FastAPI 接口文档，不是 Vue 页面。

用终端直接对照真实接口，必要时保存快照：

```bash
curl -fsS http://127.0.0.1:8000/api/robot/status | tee "$RUN/checks/api_robot_start.json"
curl -fsS http://127.0.0.1:8000/api/devices | tee "$RUN/checks/api_devices_start.json"
curl -fsS http://127.0.0.1:8000/api/robot/safety | tee "$RUN/checks/api_safety_start.json"
curl -fsS http://127.0.0.1:8000/api/camera/stream-info | tee "$RUN/checks/api_video_start.json"
```

检查经纬度是否与 `/mgx23/position` 一致、位置与 `/odom` 一致、owner 与任务状态一致、急停/障碍状态与 `/safety/status` 一致。断流后应出现 fresh=false、相机/手柄断开、未知值 null，而不是沿用正常状态。

Web 已提供三模式选择、任务编辑、开始/暂停/继续/取消和运行归档，入口与步骤见 [Web 任务操作说明](Web任务操作与旧GUI功能迁移.md)。本阶段先在静止、受控条件核对请求是否经 ROS 服务，再逐步验证实车操作。HTTP 409 表示安全/任务拒绝，503 表示服务不可用，504 表示未及时得到确认，均应记录原因；504 不证明请求没有发生。

### 12.2 前端代码与当前可用的查看方式

```bash
cd /home/zhang/agri_robot/agri_web
node --version
npm run dev -- --host 0.0.0.0 --port 5173
```

前提是已安装 package.json 对应依赖，Node 满足该文件 engines 要求。Jetson 本机浏览器访问 `http://127.0.0.1:5173`，同一局域网其他设备访问 `http://Jetson实际IP:5173`。Vite 已配置 `/api` 和 `/video` 同源代理，默认指向其所在机器的 8000/8080。前端在笔记本运行时，参照 [Web 实时数据显示与启动](Web实时数据显示与启动.md) 配置实际 Jetson 代理地址。

如现场不便直接开放 Web 端口，可在笔记本使用 SSH 转发前端端口，替换成实际 Jetson 地址与用户：

```bash
ssh -N -L 5173:127.0.0.1:5173 zhang@JETSON_IP
```

然后笔记本打开 `http://127.0.0.1:5173`，API 和视频仍由 Jetson 上的 Vite 代理。该方式仅用于现场访问；生产静态部署需额外配置反向代理。

`stream-info` 默认返回 `/video/stream?...`，已接入总览相机面板和 Vite 视频代理。视频服务与图像话题都需要启动；HTTP 连接失败显示重试提示。视频服务未启动不影响其他状态更新。

顶部急停以真实服务响应和状态反馈为准；安全状态未知时禁用解除急停。保持静止分别核验正常反馈、状态过期、复位拒绝和后端断连，确认不会用旧“已解除”状态覆盖未知。记录 API 快照和页面截图，现场停止措施仍是必要的实验保障。

## 13. 每轮结束：怎么确认数据真的留下了

顺序：先急停/明确停车并由观察人确认车体停止 → 取消尚在运行的任务使 CSV 关闭 → 保存最终状态/参数 → 等待几秒 → 各 recorder 用 Ctrl+C 正常结束 → 再结束核心和其他查看进程。不要直接断电或强杀所有进程收场。

在核心仍运行时保存参数与状态：

```bash
ros2 param dump /localization > "$RUN/checks/localization_params.yaml"
ros2 param dump /safety > "$RUN/checks/safety_params.yaml"
ros2 topic echo /safety/status --once > "$RUN/checks/safety_end.txt"
# 本轮启用了 waypoint 或 path_tracker 时，再分别 dump 对应节点。
```

正常关闭录制与核心后执行：

```bash
ros2 bag info "$RUN/bag/core" | tee "$RUN/checks/bag_info.txt"
du -sh "$RUN"
ls -lh "$RUN/raw" "$RUN/paths" "$RUN/tracks" "$RUN/safety" "$RUN/bag/core"
```

逐轮验收：

- metadata.yaml 与全部数据库分片存在，录制时间覆盖任务开始前、运行中与停车后；SQLite 包不是只有一个空目录。
- 本阶段必需 Topic 的消息数非零；检查与实测频率、实验时长是否大体一致，确认 QoS 没有导致缺录。
- S01/S02 至少有原始定位/航向、配对位姿和原点。S04/S05 还需原始 Joy/scan、三层命令、安全状态和事件。S06 再加 waypoint 状态。S07/S08 再加参考路径、tracking/error、tracking 状态和 CSV；S08 另有规划 JSON。
- 配置启用了原始数据才应有非空 `.bin`；没有路径成功或任务未启动时，不应捏造“应该有”的 JSON/CSV。把未生成及其原因填入记录表。
- `source_snapshot.tar.gz` 与实际运行参数/目标点/边界一致；检查是否误用旧地块、默认速度或另一个 RUN。
- 人工记录表补全操作时间、失败原因、独立测量和视频文件名。软件没有自动保存人工测距、操作者操作和每次失败原因说明。

至少复制一份完整 RUN 到独立存储，再进行分析；不要删除失败轮次。原始数据和视频不要随源码一股脑提交 Git，保留可定位到备份的数据索引即可。`data/experiments` 是本方案新约定，执行前不存在真实试验数据；现有代码也不会自动替你创建本方案所有子目录。

## 14. 数据怎么分析，最终应交哪些结果

| 实验 | 建议分析 | 不能混淆的内容 |
| --- | --- | --- |
| 静态定位 | 局部 x/y 均值、标准差、P95 离散、漂移、最大间隔 | 离散小不等于绝对坐标准确；没有独立基准不能声称厘米级绝对精度 |
| 航向/位移 | 方位误差、东/北位移符号、卷尺段长误差、返回点偏差 | MGX 北零与 ROS 东零不同；网格收敛、杆臂与安装角分别处理 |
| 手动/制动 | 输入/最终命令/实车动作对照；指令归零延迟、实际刹停距离 | /cmd_vel 是指令，/vel_raw 为底盘反馈；两者均非独立定位真值 |
| 设备异常 | 断流到安全事件/最终零速度的时间、重连行为 | 配置超时与整车停止时间不同；无线接收器心跳不一定证明实体手柄连接 |
| 多点导航 | 点序、到点时刻、停留时长、独立终点误差、完成率 | 相同 GNSS 同时采点和判到点只能说明内部一致性 |
| 路径跟踪 | 横向误差 MAE/RMSE/P95/最大值、航向误差、用时、进度、人工介入 | 运行段与暂停/故障/手动段分开；相邻条带/回环不能直接全局最近点误匹配 |
| 覆盖作业 | 条带间距、重复/遗漏、转弯净空、实际轨迹覆盖 | 规划覆盖不是实车作业覆盖，地头通行不代表地头农艺作业 |
| 视频/Web | 接收频率、断流识别、实际显示延迟、API/ROS 一致性 | HTTP 仍连接不等于画面实时；页面实时显示不能代替 Bag/CSV 和独立测量 |

横向误差可使用跟踪 CSV 的 cross_track，RMSE=平方均值开根号，P95 对绝对误差取分位数；注明使用的是系统内部路径投影误差还是独立测量误差。航向误差先 wrap 到 [-π,π]，再按需要转角度。

定位节点当前协方差是未知量的高方差占位，同帧速度缺失时 twist 可能保持默认零；不要用它们直接证明已知定位精度或实际车体已经停止。实际制动结合外部视频/测距验证。

每种工况输出至少：配置表、轨迹图、误差曲线、速度曲线、安全事件时间线、重复实验统计和失败案例。原始 Bag 不会自动变成论文图表，本轮文件提供可重建的数据，离线分析程序另行实现。

## 15. 回放只在隔离环境进行

Bag 中包含非零控制与解除急停请求。不要在仍连接真实底盘的 ROS domain 原样全量回放。

初步分析先用 bag info 或离线读取；需要查看轨迹时，另开没有任何硬件/控制器的独立环境，source 后设置单独 domain，只回放观测类话题：

```bash
source /home/zhang/agri_robot/scripts/setup_environment.bash
export ROS_DOMAIN_ID=194
export ROS_LOCALHOST_ONLY=1
ros2 bag play "$RUN/bag/core" \
  --topics /odom /reference_path /localization/origin /tf /tf_static /safety/status /tracking/error \
  --clock
```

该环境中不要启动底盘或自主控制器。需要按旧消息时间复现算法时，相应节点必须显式 use_sim_time=true 并正确处理 /clock；不要把旧时间戳报错当作原实测定位故障。先保留原始数据，分析/导出写入另外的 analysis 目录，不覆盖原始 Bag。
