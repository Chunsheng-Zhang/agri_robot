# Web 超时与视频连接修复

日期：2026-10-30（Asia/Shanghai）。针对用户反复出现“后端 / ROS 未连接、后端响应超时”的现场诊断。没有启用遥控、解除急停、开始任务或发送运动指令。

本文保留首次 MJPEG 连接积累修复的记录。用户随后说明相机要求较低，网页已进一步改为默认暂停、按需单张截图预览；现行相机显示方式见 [相机低带宽预览优化](2026-10-30_相机低带宽预览优化.md)，下述 MJPEG 质量 50 为前一阶段实现。

## 故障证据

故障期间 Jetson 仍为 `10.111.61.38`，前端 5173、后端 8000 正常监听。直接访问后端、经网页代理以及经本机 Wi-Fi 地址访问 `/api/robot/status` 和 `/api/devices`，均返回 HTTP 200，耗时约 9–25 ms；`ros_connected=true`，安全状态及时更新。

与此同时，`ss -tin '( sport = :5173 )'` 显示到用户电脑 `10.111.61.95` 的多条持续大流量 TCP 连接，部分发送队列积压约 0.6–0.7 MB，RTT 约 1.6 s。`ss -nt '( sport = :8080 )'` 显示视频服务存在 12 条连接。视频链路拥塞是本次超时的重要原因；不能因为本机 HTTP 200 就认定浏览器侧正常，也不能把浏览器 2 秒内没收到查询响应直接认定为 ROS 断开。

旧相机组件卸载时只清理定时器，没有显式取消 MJPEG 下载；后台标签页也继续接收视频。由此存在旧视频请求积累及多页面同时消耗带宽的风险。现场证据未单独区分 12 条连接各自来自路由切换、重复标签页还是多个窗口，不将全部连接归因于一个未经验证的浏览器行为。

前端还存在两个会放大问题的行为：机器人状态与设备状态先一起等待，快接口结果被慢接口拖住；一旦查询失败，侧栏把“无法确认状态”笼统显示成“后端 / ROS 未连接”。

## 修改

- `CameraMonitor.vue`：组件隐藏时暂停视频和相关轮询，卸载前通过替换图像源主动取消下载；恢复可见后建立新的流。网页请求 JPEG 质量由 70 改为 50；保留 ROS 话题原始斜线，不修改相机采集设置。
- `useRealtime.ts`：状态与设备查询独立完成、独立处理失败，每路单独限制一个在途请求，轮询周期为 0.5 s。慢设备请求不会阻止下一轮机器人状态刷新。
- 页面新鲜度从请求开始时计时，保守计入完整网络往返；数据迟到不会伪装成刚采集。安全状态及一般设备使用 1 s 预算，电压保留 3 s，位姿、速度和整体快照期限仍分别为 1 s、1.5 s、2.5 s。失败或过期时不允许依赖旧状态启用运动控制。
- `http.ts`：查询超时明确指出接口与 2 s 等待时间，不直接判定 ROS 已断开；响应正文读取中止也按超时说明，不误报无效 JSON。
- `AppSidebar.vue`：分别显示“后端状态未更新”“ROS 桥接未连接”“ROS 桥接在线”等状态。

GET 查询 2 s、修改操作 20 s、遥控指令 180 ms、遥控指令有效期 0.2 s 及后端 0.5 s 无心跳释放期限均未放宽。网络恢复不自动取得运动控制权。

## 验证与实际加载

离线执行真实 TypeScript 和 Vue 响应式逻辑，HTTP、UI 生命周期均为模拟输入，不连接真实网络或 ROS：

```bash
cd /home/jetson/agri_robot
node tests/web_connection.test.cjs
node tests/web_manual_control.test.cjs
cd agri_web
npm run build
```

连接回归 9 项通过，包括慢接口不拖住快接口、单路不重复请求、延迟数据不恢复为新鲜、迟到响应不能在卸载后写回、正文中止识别、后台视频停止与卸载取消、ROS 话题斜线保留。遥控回归 7 项通过。前端类型检查和构建通过，1667 个模块。未运行真实浏览器自动化，不把离线生命周期模拟等同于所有浏览器环境验证。

为清除已经累积的旧流，仅重载托管前端：

```bash
cd /home/jetson/agri_robot
TMPDIR=/home/jetson/agri_robot/.runtime/tmp \
  agri_backend/.venv/bin/python -B .diagnostics/web_timeout/restart_frontend.py
```

脚本执行前检查安全状态新鲜、控制权为空、三轴指令为零，并验证原前端进程身份。核心、后端身份不变，设备驱动不重启；原统一启动脚本继续管理新前端。

证据保存在 `.diagnostics/web_timeout/frontend_reload.before.json` 和 `frontend_reload.after.json`。前端日志仍在 `.runtime/project/runs/20261030_141406_846568_115284/frontend.log`；这些路径属于本轮本机数据，不要求新克隆环境具备。

重载后第一次检查，旧视频连接从 12 条降为 0；新建浏览器 TCP 连接 RTT 约 6–9 ms，查询接口约 20–38 ms，ROS 桥接在线。该时刻视频尚未恢复，不能把这个 RTT 当作播放视频时的保证。随后请用户只保留一个项目标签页、Ctrl+F5 刷新，用户明确反馈“已恢复正常，不再提示超时”。这次确认的是网页通信恢复，没有进行实车遥控或动态任务验证。

用户确认后又做两次只读采样，接口约 14–18 ms、ROS 桥接在线，没有积压的视频连接；当时活动视频连接仍为 0，所以尚未验证持续前台播放的网络表现。结果保存于 `.diagnostics/web_timeout/after_user_refresh.json`。隐藏项目页面时自动暂停视频符合本次设计。
